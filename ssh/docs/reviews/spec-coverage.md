# SSH specification and portable coverage review

Reviewed 2026-11-11. Package: `neotales-ssh` `0.0.0-alpha.2`, including the current uncommitted source and tests.
I did not scan the rest of the monorepo.
No credentials, tokens, or environment files were read. This is a source review, not a new build, test run, or cross-platform certification.

## Spec

SSH has a specification. The base is the RFC 4250–4254 family, not an implementation's API. Later RFCs add algorithms and authentication methods. OpenSSH also publishes implementation extensions, some now described by Internet-Drafts or newer RFCs. An algorithm name in a catalog, a standalone codec, and an integrated client/server implementation are different coverage levels. SFTP is a separate application protocol carried over SSH. Historical SCP is not specified by the SSH RFCs. Neither `ssh_config` nor `known_hosts` is an SSH wire-protocol requirement.

- **IETF RFCs, primary protocol specifications:** [4250](https://www.rfc-editor.org/rfc/rfc4250), assigned numbers; [4251](https://www.rfc-editor.org/rfc/rfc4251), architecture and encodings; [4252](https://www.rfc-editor.org/rfc/rfc4252), authentication; [4253](https://www.rfc-editor.org/rfc/rfc4253), transport; [4254](https://www.rfc-editor.org/rfc/rfc4254), channels, sessions, X11 and TCP forwarding.
- **IETF additions:** [4256](https://www.rfc-editor.org/rfc/rfc4256), keyboard-interactive; [4335](https://www.rfc-editor.org/rfc/rfc4335), session break; [4344](https://www.rfc-editor.org/rfc/rfc4344), encryption modes; [4419](https://www.rfc-editor.org/rfc/rfc4419), DH group exchange; [4462](https://www.rfc-editor.org/rfc/rfc4462), GSSAPI authentication and KEX; [5647](https://www.rfc-editor.org/rfc/rfc5647), AES-GCM; [5656](https://www.rfc-editor.org/rfc/rfc5656), ECDH/ECDSA; [6668](https://www.rfc-editor.org/rfc/rfc6668), SHA-2 MACs; [8268](https://www.rfc-editor.org/rfc/rfc8268), additional DH groups; [8308](https://www.rfc-editor.org/rfc/rfc8308), extension negotiation; [8332](https://www.rfc-editor.org/rfc/rfc8332), RSA/SHA-2; [8709](https://www.rfc-editor.org/rfc/rfc8709), Ed25519/Ed448; [8731](https://www.rfc-editor.org/rfc/rfc8731), Curve25519/Curve448. These documents were fetched, not inferred from algorithm names.
- **IETF deprecation:** [8758](https://www.rfc-editor.org/rfc/rfc8758) deprecates RC4 and moves RFC 4345 to Historic. RC4 support is not a desirable completeness target.
- **OpenSSH vendor extension document:** [`PROTOCOL`](https://github.com/openssh/openssh-portable/blob/268bdcb0c80876d97abdc74a1ca8992a1fdf7652/PROTOCOL), read at commit `268bdcb0c80876d97abdc74a1ca8992a1fdf7652`. Sections 1.2, 1.5–1.10 and 2.3–2.5 cover delayed compression, encrypt-then-MAC, OpenSSH AES-GCM negotiation, ChaCha20-Poly1305, transport ping, strict KEX, ext-info during authentication, tun, streamlocal and host-key rotation. In particular, ping uses transport messages **192 and 193**, not a global request named `ping@openssh.com`. Strict KEX is delegated there to `draft-miller-sshm-strict-kex`.
- **OpenSSH vendor format documents:** [`PROTOCOL.certkeys`](https://github.com/openssh/openssh-portable/blob/V_9_9_P2/PROTOCOL.certkeys) and [`PROTOCOL.chacha20poly1305`](https://github.com/openssh/openssh-portable/blob/V_9_9_P2/PROTOCOL.chacha20poly1305), read at `V_9_9_P2`; [`PROTOCOL.key`](https://github.com/openssh/openssh-portable/blob/268bdcb0c80876d97abdc74a1ca8992a1fdf7652/PROTOCOL.key), [`PROTOCOL.agent`](https://github.com/openssh/openssh-portable/blob/268bdcb0c80876d97abdc74a1ca8992a1fdf7652/PROTOCOL.agent), and [`PROTOCOL.u2f`](https://github.com/openssh/openssh-portable/blob/268bdcb0c80876d97abdc74a1ca8992a1fdf7652/PROTOCOL.u2f). These specify certificates, private-key format, agent extensions and security-key signatures. The old `PROTOCOL.certkeys` URL on master returns 404; the versioned document remains available.
- **Agent standard:** [RFC 9987](https://www.rfc-editor.org/rfc/rfc9987), May 2026, is the SSH agent protocol specification. Section 7 includes agent forwarding and the historical `auth-agent-req@openssh.com` / `auth-agent@openssh.com` names. Current OpenSSH `PROTOCOL.agent` points to this RFC and specifies additional session-binding and destination-constraint extensions.
- **SFTP draft, not an RFC:** [`draft-ietf-secsh-filexfer-02`](https://www.ietf.org/archive/id/draft-ietf-secsh-filexfer-02.txt), version 3. OpenSSH `PROTOCOL` section 4 adds the reversed SYMLINK convention and named SFTP extensions.
- **Post-quantum draft implementations:** Go `ssh/mlkem.go` cites `draft-kampanakis-curdle-ssh-pq-ke-05` section 2.3.3. Go `ssh/doc.go` cites [`draft-sfluhrer-ssh-mldsa-08`](https://datatracker.ietf.org/doc/html/draft-sfluhrer-ssh-mldsa-08) for its conditional ML-DSA support. These are draft-based features, not claims that RFC 4253 specifies those algorithms.
- **Historical SCP implementation evidence, not a protocol standard:** libssh 0.12.2 `src/scp.c` and `libssh.h`'s deprecated `ssh_scp_*` API. An SSH `exec` request only transports the command; it does not specify SCP's byte protocol or the remote shell's quoting rules.

## Gaps that matter

Every absence below follows a search of this crate's `src/` and `tests/`, followed by inspection of the relevant public API and handlers. Searches included algorithm names, `ext_info`, `signal`, `window-change`, `break`, `streamlocal`, `x11`, `auth-agent`, `tun@`, `hostbased`, named-pipe/vsock/socket types and `cfg(unix)`. No implementation was found where the table says `no`. A generic channel request is not counted as an implementation of its feature's payload, ordering, policy and dispatch.

### Transport, identities and authentication

- **Host-key reachability and certificates — both client and server.** Go supports multiple host-key signers, RSA/SHA-2, ECDSA and certificate handshakes. libssh supports RSA/ECDSA host keys and certificate user identities. This crate has tested RSA/ECDSA primitives in `src/rsa_hostkey.rs` and `src/ecdsa_hostkey.rs`, plus certificate re-exports in `src/cert.rs`. Its actual `SUPPORTED_HOST_KEY_ALGORITHMS` in `src/msg/kexinit.rs` contains only `ssh-ed25519`. `ClientConfig` verifies Ed25519 and `ServerConfig` owns an `Ed25519Signer`. I searched both handshakes and found no alternate host-key or certificate path. `KnownHosts::check` returns `CertificateAuthority` on an exact CA-blob match; its own module documentation explicitly says that is not certificate validation. Go's `knownhosts.New` integrates `CertChecker`; this crate does not.
- **Algorithm breadth — both.** Go's `kexAlgoMap` supports P-384/P-521 ECDH, group14/SHA-256 and DH group exchange. libssh 0.12.2 `src/kex.c` additionally lists group18, sntrup761 hybrids and ML-KEM/NIST hybrids, subject to build guards. This crate's implemented handshakes cover ML-KEM768/X25519, Curve25519 including its libssh alias, P-256 ECDH and group16/SHA-512. I searched `src/kex/` and the supported catalog and found no other mechanisms. AES-192-CTR and HMAC-SHA1 supported by Go/libssh are also absent from the crate's supported catalog. Deprecated SHA-1 KEX, CBC/3DES and RC4 interoperability are not reasons to expand the secure default policy.
- **Public-key authentication breadth — both.** `src/auth.rs` integrates Ed25519, RSA/SHA-256 and P-256, including agent-backed versions. Its standalone RSA/SHA-512 and P-384/P-521 host-key primitives do not make those authentication algorithms usable. I searched `PublicKeySigner`, `AgentKeySigner` selection and server verification and found no integrated RSA/SHA-512, P-384/P-521, certificate or security-key authentication. Go and libssh have broader key support. Go v0.59.0 also has ML-DSA and vendor-named ML-DSA certificates under the stated Go build guard. The crate has no ML-DSA implementation.
- **Private-key formats — both programs loading identities.** Go's `keys.go` imports PKCS#1, PKCS#8, EC PEM and OpenSSH containers. libssh exposes private-key import/export in `libssh.h`. This crate's `src/openssh_key.rs` accepts the binary OpenSSH container only, with one Ed25519, RSA or P-256 key and either no encryption or bcrypt/AES-256-CTR. I searched its parser and found no PEM/PKCS import, P-384/P-521 private-key import or private-key export API. This limits identity-file compatibility on every platform; it is not a Unix restriction.
- **Authentication negotiation and repeated challenges — both.** Go supports method discovery, normal failure fallback, retryable methods, repeated keyboard-interactive exchanges, none-auth success and configurable partial-success policies. libssh exposes none, method lists, keyboard-interactive exchanges and partial success. In `src/auth.rs`, `ClientAuthMethod` has only public-key, password and one-round keyboard-interactive variants. A normal failure returns `HardFailure`; only `partial_success = true` advances to another method. `tests/userauth.rs::partial_success_false_stops_before_the_second_method` explicitly fixes that behavior. The server rejects none; it only exposes password partial success, not Go's general next-callback policy. I searched these APIs and handlers and found no none-success or repeated-challenge path. This blocks ordinary portable authentication fallback and multi-round MFA, not just an optional UI convenience.
- **GSSAPI — client and server, plus libssh-only GSS KEX.** Go supplies real MIC-oriented client/server mechanism interfaces. libssh supplies MIC, credentials and GSS KEX integration when built for it. This crate's `ClientAuthMethod` has no GSSAPI variant. Its server token callback in `src/auth.rs::handle_gssapi_packet_inner` accepts tokens and message 63, but does not handle message 66 or verify the session/user/service MIC. `src/gssapi.rs` defines the MIC message number without an implemented MIC exchange. RFC 4462 §§3.5–3.6 distinguishes MIC-capable contexts from the exceptional no-integrity acknowledgement path; message 63 is not a substitute for MIC. The ordinary unauthenticated transport also cannot deliver these follow-up packets to that callback. `tests/gssapi.rs` proves framing/callback behavior, not portable GSSAPI login. I found no GSS KEX implementation. No particular Kerberos/libc dependency is forced today because no mechanism is bundled.
- **Extension negotiation and signature selection — both.** Go and libssh integrate RFC 8308. This crate's `src/msg/ext_info.rs` has `ExtInfo` and RSA preference helpers, tested in `tests/ext_info.rs`. I searched `src/transport.rs`, both handshakes and `src/auth.rs` and found no integrated ext-info receive/send or `server-sig-algs` consumption. A public codec is not negotiation coverage.
- **Compression — both when talking to libssh/OpenSSH.** libssh has stateful delayed zlib; Go only negotiates `none`. This crate advertises `zlib@openssh.com`, but `src/compression.rs::compress_payload` creates and finishes a fresh `ZlibEncoder` for every packet. `src/cipher.rs` compresses whenever the selected protector says zlib; no authentication activation gate was found. RFC 4253 §6.2 requires a continuous compression context, and OpenSSH's delayed extension activates after authentication. `tests/compression.rs` exercises local primitives, not that peer-compatible lifecycle. This is a protocol gap on every platform, not a libc gap.
- **Configurable public transport proposals — both.** Go exposes `Config`; libssh exposes algorithm options. This crate exposes `ClientConfig::with_kexinit` and `ServerConfig::with_kexinit`, but the `KexInit` definition is inside private `msg`. I inspected `src/lib.rs` and found no production public re-export. `docs/visibility.md` records the same public-surface problem. White-box tests including private source do not make that type available to consumers.

### Sessions and application protocols

- **Signal, window-change and break — both.** Go has client `Signal` and `WindowChange` and raw server requests. libssh has named signal, resize and break APIs/callbacks. This crate implements `exit-signal`, which is a different server-to-client message. I searched `src/session.rs` and found no signal, resize or break request implementation. `ServerSessions::handle_request` rejects unsupported requests. `ChannelConnection::send_request` remains a raw escape hatch, not portable session support.
- **SFTP extensions, interoperability and pipeline — client.** libssh exposes asynchronous requests, statvfs/fstatvfs, hardlink, fsync, lsetstat, limits, path expansion, home directory and UID/GID-name lookup in `sftp.h`; `src/sftp.c::sftp_rename` uses the OpenSSH POSIX-rename extension. This crate records extension advertisements but implements no extended operation and permits only one outstanding request (`src/sftp.rs`). I searched its operations and found no extension dispatch or asynchronous request API. Its SYMLINK payload uses draft order, asserted by `tests/sftp.rs::symlink_and_rename_use_the_draft_field_order`. OpenSSH `PROTOCOL` §4.1 specifies the reversed order used by libssh. Thus the common OpenSSH peer convention is not covered by the current helper. `request_sftp` now exists; claiming the subsystem request itself is missing would be wrong.
- **SCP limits and remote-shell assumptions — client.** libssh's deprecated API supports recursive directories and streaming file bodies. This crate deliberately handles one regular file, materializes it under a 64 MiB bound, and rejects directory records (`src/scp.rs`). That is a libssh parity limitation, not a missing SSH transport feature. The new `request_scp_upload` and `request_scp_download` correctly send the generated command as `exec` (`src/session.rs`, tested in `tests/session_channel.rs`). However, `src/scp.rs::build_command` uses POSIX single-quote escaping and `/` basename rules. It does not support arbitrary Windows remote-shell syntax or Windows path separators. The byte protocol is portable; these convenience helpers are not remote-shell-neutral. I found no alternate quoting/path policy.
- **Client configuration subset — client.** libssh implements config parsing and includes (`ssh_options_parse_config`, `LS:src/config.c`). Go does not implement `ssh_config`. This crate resolves selected Host/Match fields and explicit SendEnv/SetEnv, but rejects `Include` and preserves other unsupported keywords (`src/ssh_config.rs`, `tests/ssh_config.rs::include_is_rejected_without_being_read`). File loading, home expansion and command execution are deliberate caller responsibilities, not defects. The narrower accepted configuration language remains a libssh compatibility gap; receiving `KexAlgorithms` as text does not apply it to a transport.

### Forwarding and liveness

- **Remote port allocation and forwarding endpoints — client and server.** Go's `ListenTCP` and libssh's listen/reply APIs support requested port zero and return the allocated port. `src/tcpip_forward.rs::handle_global_request` explicitly rejects zero; `TcpipForwardResponse` carries no allocated port. `tests/tcpip_forward.rs::port_zero_and_callback_panic_are_denials` proves the restriction. The direct/forwarded channel metadata and fixed-port data flow exist. No listener or socket pump is supplied, by design. Record this protocol allocation/reply gap for later tunnels work; do not treat metadata-only forwarding as a dev-tunnel product.
- **Streamlocal — both protocol roles.** Go has direct and reverse streamlocal helpers; libssh exposes `ssh_channel_open_forward_unix` for direct streamlocal. I searched this crate and found no direct-streamlocal, forwarded-streamlocal, streamlocal-forward or cancel-streamlocal-forward codec/dispatcher. A remote Unix-domain endpoint does not require the client host itself to be Unix, so omitting the wire protocol also limits Windows clients.
- **Agent forwarding — both.** Go's agent package provides request and bridge helpers. libssh exposes both request and channel-open callbacks. I searched this crate and found no `auth-agent-req@openssh.com` session support or `auth-agent@openssh.com` channel dispatcher. `AgentClient` is a local signing client, not forwarding. This is a protocol gap in addition to the platform-specific local connector gap.
- **X11 — both.** libssh exposes X11 request/open helpers and callbacks. Go exposes only generic channel/request facilities. I searched this crate and found no X11 request, cookie or channel handling. Local display integration is application work; absent SSH X11 framing is the comparison gap.
- **Keepalive and actual OpenSSH ping — both.** libssh's `ssh_send_keepalive` requests a reply. Go exposes generic global requests and v0.59.0 responds to transport ping in `mux.onePacket`; its server advertises ping in ext-info. This crate's `GlobalRequest::keepalive()` sets `want_reply = false`, so that default cannot establish liveness. Callers can explicitly request a reply, but no timer/liveness policy is integrated. More importantly, `src/keepalive.rs::encode_ping` emits a global request named `ping@openssh.com`. OpenSSH specifies transport messages 192/193. I searched the transport and channel handlers and found no implementation of those messages. `tests/keepalive.rs` tests the crate's invented global-request shape, not OpenSSH ping compatibility.

### Platform I/O and agent service

- **Native agent connection — Windows client gap now; mobile integration gap later.** `src/agent.rs::AgentClient<T>` is portable over `Read + Write`. The only built-in connector is `connect_unix`, using `std::os::unix::net::UnixStream` behind `cfg(unix)`. On Windows the same function returns `UnsupportedPlatform` with `AgentClient<io::Empty>`. I searched and found no named-pipe connector. `socket_path_from_env` is now implemented and tested; it selects from a supplied map and never reads the process environment. It does not turn a path into a Windows pipe connection. Linux/macOS Unix-agent interoperability is recorded in `docs/compatibility.md`; that document explicitly excludes Windows agent lanes. Do not count a Unix-only connector as full portable agent coverage.
- **Mobile sandbox and desktop-agent assumptions.** Android and iOS satisfy Unix-target code paths, but a pathname Unix socket does not confer access to another application's or desktop login agent's socket. The generic agent transport is reusable; the native local-agent convenience API assumes a reachable filesystem socket. No platform agent provider, sandbox bridge or mobile agent integration was found. This is an integration blocker for that feature, not a reason to mark the entire SSH core Unix-only.
- **Agent operations and agent server — both kinds of program.** Go's `Agent`/`ExtendedAgent` support adding/removing keys, locking/unlocking, constraints and extensions; `ServeAgent` and `NewKeyring` provide an agent service. This crate's `src/agent.rs` only lists and signs. I searched it and found no mutation/lock/constraint/extension operations and no server/keyring. `sign_with_flags` accepts an explicit flags word, but the default algorithm selection and `AgentKeySigner` are narrower. libssh is an agent authentication consumer, not an in-process agent-server comparator.
- **No discovered libc-specific production API.** The sole explicit OS-specific production transport found is the agent Unix connector. The SSH handshakes, channel protocols, direct/reverse TCP metadata, proxy callbacks, SFTP and SCP byte streams do not require `TcpStream`, a raw Unix fd, or `libc`. `Cargo.toml` declares `nix` only as a Unix dev-dependency. `src/compression.rs` describes a pure-Rust flate2 backend, but the inherited workspace feature/version selection was outside this review's allowed scope. Android/iOS and alternative-libc dependency build support therefore remains unverified, not established by inspection of this leaf manifest.
- **Tests are not a mobile runtime contract.** Unix-only OpenSSH test helpers use permission, process-group and process APIs (`tests/openssh_tools/temp_dir.rs`); live tests launch desktop OpenSSH tools and use TCP (`tests/openssh_interop.rs`, `tests/openssh_identities.rs`, `tests/openssh_channels.rs`). These assumptions block reuse of those live lanes in mobile sandboxes, not the stream-oriented production core. `docs/compatibility.md` records earlier Linux/macOS/Windows client results, not current CI certification, mobile results or reverse server interoperability.

## Not required

- **Process spawning, shell execution, native PTY creation, environment discovery and socket pumping are application responsibilities.** This crate intentionally exposes policy and bytes. Go's SSH server API also delegates session execution. Do not demand an in-process operating-system login server to satisfy the session wire protocol. The absence of `x/crypto/ssh/terminal` is not an SSH protocol defect.
- **Reading the process environment is intentionally refused.** `EnvironmentPlan` consumes an explicit map. `SendEnv` selects supplied values; `SetEnv` overrides them. `socket_path_from_env` consumes an explicit map as well. `tests/environment.rs`, `tests/agent.rs` and `tests/session_channel.rs` cover this work. No implicit environment read is required.
- **An in-process SFTP server is intentionally absent.** libssh's `WITH_SERVER` API has one; Go's SSH package does not. Record the difference, but do not classify this deliberately excluded product feature as a defect.
- **Recursive SCP is intentionally refused.** The table records its libssh parity limit. It is not an instruction to remove the single-file safety boundary or revive deprecated SCP as the preferred transfer protocol.
- **OpenSSH tun channels are not comparator requirements.** I searched Go v0.59.0 SSH source and libssh 0.12.2 headers/source and found no dedicated `tun@openssh.com` implementation. Generic arbitrary channels do not make either a tunnel-device library. Native TUN/TAP devices are outside this review.
- **Native vsock and named-pipe dialing are not features supplied by either reviewed comparator.** I searched their SSH source/headers and found no dedicated vsock API or Windows named-pipe agent connector. Go accepts supplied `net.Conn`; libssh uses `socket_t` and agent channel/socket setters. This crate's byte-stream API does not prevent a caller-supplied adapter. Windows native agent usability is still a product platform gap, even without comparator parity pressure.
- **Deprecated algorithms are not default-policy requirements.** RFC 8758 explicitly deprecates RC4. Go retains insecure opt-in algorithms but no longer supports DSA (`G:keys.go`). No requirement follows to advertise every historical algorithm named in RFC 4253 or every insecure comparator option.
- **Hostbased authentication, OpenSSH connection multiplexing and host-key rotation are not demonstrated comparator feature requirements here.** Searches found no dedicated hostbased-auth or OpenSSH mux implementation in either reviewed library. libssh marks `UpdateHostKeys` unsupported in `src/config.c`; Go can surface an arbitrary global request but does not implement the host-key proof/update workflow. Do not equate extension pass-through with a supported feature.

## Verdict

SSH is specified, but this crate does not cover the combined Go v0.59.0 and libssh 0.12.2 feature set for a portable client and server. Its stream-oriented core works toward Linux, Windows and macOS without forcing Unix sockets into the transport API, but native agent access remains Unix-only and mobile dependency/runtime support is unverified. The largest holes are integrated host-key/certificate breadth, authentication negotiation and GSSAPI MIC, ext-info/compression correctness, missing session controls, SFTP extension compatibility and forwarding extensions/port allocation. The new environment, subsystem, SCP-request and explicit agent-path APIs close real surface gaps; they do not establish full protocol or platform coverage.
